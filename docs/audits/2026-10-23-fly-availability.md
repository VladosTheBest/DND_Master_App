# Fly.io: длительная недоступность до ручного рестарта

Сверка: 23 октября 2026 года. Область: read-only production-диагностика и код обработки хранилища. Приложение: `dnd-master-app`, регион `ams`, одна машина, release 177. В ходе диагностики машина не перезапускалась, настройки и production-данные не менялись.

## Исправление

Реализованы фоновый storage probe (3 с), атомарный readiness без блокировки на транзакции, отдельный публичный `/livez` и callback завершения небезопасного writer. Потеря Ping/Begin и неопределённый COMMIT приводят к завершению Go-процесса; исходная SQL-state и advisory lock заново загружаются при старте. Внутрипроцессный reconnect со старым кешем не используется.

Docker supervisor `scripts/run-server.sh` повторяет запуск без конечного лимита с backoff 1/2/4/8/16/30 с, сбрасывает его после 60 с работы, прекращает повторы по TERM/INT, очищает process group старого сервера вместе с Codex/image helpers. Maintenance-команды не повторяются. `util-linux` явно включён в образ для `setsid`. Неопределённый исход платной AI-операции не вызывает автоматический повтор генерации: прежние активные jobs после рестарта по-прежнему становятся failed для проверки мастером.

Проверены: полный Go suite; wire-тест реального pgx TCP-соединения с исчезновением peer после успешного Ping, ошибкой BEGIN и потерей ответа COMMIT; сохранение fail-closed/cache invariants, неблокирующий readiness, liveness 200 при readiness/API 503, однократное уведомление и остановка monitor. Это изолированный протокольный peer, не полноценная PostgreSQL failover-лаборатория; existing SQL/S3 integration suite без отдельной тестовой БД пропускается. Supervisor прошёл локально и в Linux VM Fly на искусственном worker в `/tmp`: два неудачных запуска → восстановление, отсутствие двух writers, TERM, cleanup helper и одноразовая maintenance-команда. Пользовательский сервер для этого теста не останавливался; production-БД не отключалась.

Диагностическая часть ниже описывает версию до исправления. Первопричина первого сетевого/SQL-сбоя по историческим логам остаётся неустановленной.

## Вывод и степень уверенности

**Автоматический сон исключён действующей конфигурацией:** у машины `autostop=false`, `autostart=true`, `min_machines_running=1`; эти значения совпадают с [fly.toml](../../fly.toml).

**Подтверждена причина отсутствия автоматического восстановления на уровне кода:** [cloudDatabase.check](../../apps/server/internal/httpapi/cloud_postgres.go) после единственной ошибки `Ping` ставит `failed=true`. Следующие вызовы возвращают `database state requires restart`, не выполняя новый Ping или reconnect. Аналогичный флаг ставится при ошибке Begin и неопределённом исходе Commit. [server.go](../../apps/server/internal/httpapi/server.go) вызывает эту проверку перед маршрутизацией любого запроса, включая `/`, статические файлы и `/healthz`, и возвращает 503 `storage_unavailable`.

**Реальный инцидент согласуется с этим механизмом:** failed health check → ошибки маршрутизации → отсутствие самостоятельного восстановления → passing сразу после ручного рестарта. Но первоначальная ошибка БД и внутренний флаг процесса до рестарта не были залогированы и сейчас недоступны. Поэтому точный первый триггер — кратковременная потеря соединения, таймаут, ошибка Begin/Commit либо другая причина зависания — по сохранённым данным не доказан. Это не подтверждённое расследование аварии PostgreSQL как сервиса.

## Почему Fly сам не исправляет это состояние

Действующая restart policy машины — `on-failure`, `max_retries=10`. Она не заменяет автоматическое восстановление работающего, но нездорового процесса.

В [официальной документации Fly health checks](https://docs.fly.io/reference/health-checks) явно указано: failed service check прекращает маршрутизацию, но сам по себе не перезапускает и не останавливает машину. [Autostop/autostart](https://docs.fly.io/launch/autostop-autostart) управляет остановленными/приостановленными машинами; в данной конфигурации autostop выключен, процесс оставался запущенным.

Получается цепочка, которую текущий код допускает:

1. Проверка соединения с БД не проходит один раз.
2. Включается необратимый до рестарта `failed`.
3. Все HTTP-запросы, в том числе health check, получают 503.
4. Fly перестаёт направлять запросы на единственную машину. Запасной здоровой машины нет.
5. Процесс не завершается; `on-failure` не срабатывает.
6. Ручной рестарт пересоздаёт соединение, заново захватывает advisory lock и загружает SQL-state; сервер снова работает.

Дополнительный риск: проверка и SQL-операции используют общий mutex одной connection; транзакция может иметь deadline до 45 секунд, тогда как HTTP health check Fly ждёт 5 секунд. Долгое ожидание mutex также может давать временный failed health check. Это отдельный возможный механизм; его участие в данном инциденте не установлено.

## Текущее состояние при проверке

- Одна машина `started`, HostStatus `ok`, service check `passing`.
- Managed PostgreSQL `shadow-edge-db`: `ready`, одна replica, 4,7 ГБ из 20 ГБ занято по `fly mpg status`. Поля `disk=0/replicas=0` из `mpg list` не использовались как доказательство размера/числа реплик: подробный status показал реальные значения.
- Внутри VM `/healthz` через loopback — HTTP 200, `status: ok`.
- Снаружи `/healthz` — 200 примерно за 287 мс; `/` — 200 за 159 мс; `/api/auth/session` — 200 за 117 мс. Это единичные пробы, не статистика SLA.
- `/data`: около 52% занято, 889 МБ доступно.
- В VM около 575 МиБ MemAvailable из примерно 962 МиБ MemTotal после рестарта. Это не измерение потребления памяти в момент сбоя.
- Последний останов был запрошен пользователем и не был OOM kill. Отсутствие OOM в этом событии не исключает исторические проблемы памяти, не попавшие в доступный буфер.

## Приоритет исправления

Это самостоятельная **P1-задача доступности**, которую следует делать раньше визуального редизайна.

1. **Наблюдаемость причины.** Логировать переходы storage healthy/degraded/failed, тип операции, безопасную классификацию ошибки/SQLSTATE, длительность, первый сбой и recovery. Не выводить DSN, credentials, пользовательские payload и токены. Не повторять один и тот же лог на каждый запрос.
2. **Восстановление с сохранением инвариантов.** Отличить краткий сбой проверки от потери writer connection и неопределённого COMMIT. Самый небольшой безопасный путь для текущей архитектуры — ограниченная повторная проверка с задержками, затем управляемое завершение нездорового процесса, чтобы supervisor запустил его с полным чтением SQL-state и повторным захватом advisory lock. Политику restart/retry/backoff проверить на длительном отказе БД, чтобы не исчерпать 10 попыток и не устроить restart storm.
3. **Разделить liveness и readiness.** Liveness отвечает, что процесс работает; readiness — что он безопасно обслуживает данные. Service check должен отражать реальную готовность, а не всегда отдавать 200. Статическую страницу состояния можно отдавать отдельно, но это не восстанавливает API.
4. **Снизить зависимость probe от общей SQL-блокировки.** Общая фоновая проверка/снимок readiness с временем последнего успеха; исключить лишний Ping на пользовательском пути. Задержка health probe должна быть предсказуемой при обычной транзакции.
5. **Изолированная отказная проверка до deploy.** Потеря соединения после idle, timeout Ping, длительная транзакция, Begin failure, недоступность БД несколько минут, неопределённый COMMIT, занятый advisory lock. Проверить перезапуск, отсутствие тихой потери сохранённых данных и отсутствие второго writer.
6. **Проверка после публикации.** Readiness, внутренний/публичный HTTP, read-only доступ к сохранённым данным и понятная судьба незавершённых AI-задач. Нынешняя реализация после рестарта помечает активные jobs ошибкой; нельзя автоматически повторять платную работу с неизвестным исходом.

**Не применять как быстрый обход:** постоянно сбрасывать `failed`, незаметно переподключать conn без пересборки кеша/lock, сделать health check безусловно успешным, включить второй writer или просто добавить вторую машину. Бэкенд сейчас использует cache в памяти и session advisory lock; после потери соединения старый процесс не может безопасно продолжать запись из прежнего кеша.

## Воспроизводимые команды диагностики

```powershell
fly status -a dnd-master-app
fly checks list -a dnd-master-app
fly machine list -a dnd-master-app
fly machine status d89064ef0e3758 -a dnd-master-app
fly machine status d89064ef0e3758 -a dnd-master-app -d
fly logs -a dnd-master-app --machine d89064ef0e3758 --no-tail
fly logs -a dnd-master-app --no-tail
fly releases -a dnd-master-app --json
fly mpg list -o personal --json
fly mpg status 1zvn90k136vrkpew
```

`--no-tail` читает доступный буфер, не полную историю инцидентов. В текущем приложении ошибка `cloud.check` возвращается клиенту, но причина не записывается в серверный журнал. Точную первопричину прошлого обрыва нельзя восстановить одной повторной командой logs.

Историческая диагностика выполнена без изменения production-данных; реализованное исправление и фактические проверки описаны выше. Связанный общий аудит: [сайт, UX/API и производительность](2026-10-23-site-audit.md).
